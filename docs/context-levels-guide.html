Enhance Prompt / Context guide / v0.5.2

Context Level controls what the rewriter learns about your project.

It starts with the project attached to your Copilot session. Each level adds different sources, filters them, and gives the rewriting model a limited set of excerpts. It does not give that model your entire repository.

  1. 01 →Your request + sessionThe task you type and the attached project folder.
  2. 02 →Gather contextThe selected level, file permissions, exclusions and size limits decide what to include.
  3. 03 →Rewrite the promptThe Effort assignment chooses the model; Style and Structure guide the wording.
  4. 04Review, then sendThe result is a prompt for Copilot to act on. Enhancement itself does not implement the task.

Three different controls: Context Level chooses project information. Style chooses the approach to the task. Effort chooses a model assignment, not the amount of project context.

What happened to Basic?

A saved Basic (saved): project identity only choice still works, with a roughly 1,000-character allowance for Workspace and Target agent. It is not offered as a new choice. The same basic behavior is used when project file access is disabled. Existing saved defaults are preserved; the default for a new installation is Project overview.

Internal names remain off, basic, standard, deep and max for compatibility. The interface’s clearer names do not describe five new algorithms.

Where those context entries actually come from

Paths below are relative to the project folder attached to the Copilot session that opened the panel. For example, if that folder is C:\Projects\storefront, then README.md means C:\Projects\storefront\README.md. Your screenshot alone does not identify that folder.

Workspace — generated project identity, not a file

The Copilot adapter asks the session for metadata.snapshot().workingDirectory, requires a local absolute path, and resolves its real location. It uses that folder’s name and path to build the Workspace entry.

Illustrative Workspace content:
C:\Projects\storefront: storefront

There is no “Workspace” document to open. It does not include all files or a chat transcript. The current adapter does not supply a branch in this summary; Git status at the higher levels supplies branch information separately. An unknown or remote project root does not cause the plugin to read its own installation folder instead.

Target agent — Copilot’s identity and activity state, not the rewriting model
Illustrative Target agent content:
copilot (waiting)

This is generated from the attached session. It names the destination agent and its state: waiting, working, blocked or unknown. The state comes from activity, processing, queued work and pending permissions. It is not a file, the agent’s full instructions, the chat history, or the Claude/GPT model selected through Effort. The agent identity can also guide the rewriter’s target-specific instructions when adaptation is enabled.

CONTRIBUTING.md and other project instructions — real files, bounded excerpts

CONTRIBUTING.md is an optional file at the project root. It commonly describes contribution, coding and testing conventions. The plugin reads whatever your project actually puts there; it does not generate that file.

The collection order is: configured Extra context files first, then the following known paths, then up to four .md/.mdc files found under .cursor/rules/. Duplicate paths in that instruction list are removed.

Each instruction/extra file gets up to approximately 4,000 characters. All instruction files, extra files and the README digest share a 9,000-character allowance. Earlier files can consume it, leaving later files or README out. Increasing Context Level does not enlarge this allowance.

These are specific paths relative to the attached project root. There is no general recursive search for every nested AGENTS.md or for instructions in parent/home directories. A nested instruction file can be included explicitly as an extra file; it is not automatically inherited here.

README.md — a deterministic digest of a real root file

The plugin finds a root README, README.md, README.rst or README.txt (case-insensitive). It takes an introductory excerpt and sections with Markdown headings matching setup, installation, usage, development, testing, build/run, contributing, architecture, structure, overview, stack, scripts or commands.

This is text extraction, not an AI summary. It recognizes Markdown headings through level four; RST headings are not parsed as Markdown headings. The introduction gets at most one quarter of the available digest size. The whole digest is capped near 3,500 characters and can be smaller because it shares the instruction allowance. It can omit later sections even if they are relevant.

Open the original in a text editor to see the whole document. The original will not necessarily match the included excerpt: content can be masked, selected or shortened.

Stack and commands — generated from manifests and build files

This is a summary, not a separate file. At the root, package.json can provide the project name, package manager, up to 30 dependency names and 25 scripts. Permitted lockfile names help infer the package manager; commands are shortened. A root tsconfig.json signals TypeScript.

Other recognized sources include Python’s pyproject.toml/requirements.txt, go.mod, Cargo.toml, Makefile and justfile. Maven, Gradle, Composer, Bundler, .NET, Flutter and Docker can be recognized by root filenames. Some command hints are conventional, such as cargo test, rather than extracted scripts.

Up to five .github/workflows/ paths are listed as CI hints. Their contents are not loaded by stack detection. Nested package manifests are not recursively summarized. The plugin reads these clues; it does not execute build or test commands to gather context. Stack text reads allow up to 300,000 bytes per manifest, while ordinary instruction/source reads allow 200,000.

Repository tree — a generated map, not the contents of every file

With Git available and allowed, the plugin lists tracked and non-ignored untracked paths, capped at 50,000 entries before deduplication/filtering. Otherwise it walks the filesystem with limits of 8,000 files and six directory levels, skipping common dependency/build/cache directories and most hidden directories (supported .github and .cursor paths remain eligible).

The summary shows directories through depth two with descendant file counts, followed by root filenames. It keeps up to 70 lines, plus an omission marker. “Repository tree (81 files)” means 81 eligible listed file paths, not 81 file contents sent to the model. The count is a filtered, bounded inventory, not a promise to enumerate the whole repository. Git and filesystem listing differ; do not assume every generated folder is excluded when Git tracks it.

Turning off Git switches to filesystem walking; that walker uses its own skip rules and does not parse .gitignore. Use the plugin’s Excluded paths for exclusions you need in either mode.

Git context — current changes and recent history, at Relevant code and AI-assisted

Three independent reads gather: current branch/status with up to 60 permitted change entries; the six latest non-merge commit summaries (short hash, subject and relative time); and uncommitted changes compared with HEAD, including staged and unstaged tracked changes.

The diff has a file-stat summary and a patch with two surrounding lines. Its patch body is limited near 5,000 characters for Relevant code or 9,000 for AI-assisted, plus summary/truncation text. Untracked file contents are not part of git diff HEAD; those files may still qualify for source snippets. No Git repository, disabled Git or failed Git reads can leave these entries absent while local context continues.

Exclusions and sensitive-file checks filter status and diff paths, including both sides of renames. Diff/search path rules also omit names containing lock, minified files and source maps. If too many diff exclusions are needed (over 300), the diff is omitted. Recent commit subjects are repository-wide text, not filtered to selected files, so a subject can still mention an excluded filename.

Unchecking the Git status item keeps it out of the payload, but status can still be read locally to prioritize changed files. Disable Git in privacy settings to prevent the Git reads themselves.

“Relevant” means ranked candidates, not proven dependencies

Relevant code and AI-assisted both start with the same local search. Neither parses a full dependency graph, runs your app, or proves which file caused a bug.

1. Turn your request into weighted search terms

The plugin extracts up to 12 keywords. Exact paths, backtick-quoted text, dotted names and filenames get strong weight; identifiers such as refreshSession are stronger than generic words. Common filler words are dropped. At most eight keywords of at least four characters are used for content search.

For example, Fix the login timeout in src/auth/session.ts gives the selector much better clues than Fix this. Input is accepted as Unicode, but keyword extraction is largely identifier/ASCII-oriented; non-English prose may produce fewer useful local terms.

2. Search permitted files locally and rank them

Git search uses case-insensitive literal string matches. Without Git search, a bounded fallback tries likely paths first and stops after 300 candidate-file attempts, 4 MB of text or about 1.5 seconds. A read already underway can make that time limit slightly longer. If it stops early, the context notes say so.

Path matches, content matches and changed files raise a file’s score. Rare content matches count more than words found across many files. Fixtures, snapshots, migrations, generated code and locale directories receive lower scores; test files get a smaller penalty unless the request mentions tests. Instruction files already included do not compete again. Other prose files only compete when their paths start with docs/.

Files with no positive score are not local selections. Relevant code keeps up to six highest-ranked paths; AI-assisted starts with up to ten local choices. A locally searched file does not automatically become model input. The small snippet allowance limits what is sent, not necessarily every local file read by search.

3. AI-assisted only: ask a model to choose from filenames

The selector receives your request plus up to 600 permitted candidate paths. Up to 150 top local matches lead that list, then the remaining eligible paths fill it. It receives no file bodies in this selection step and cannot browse the repository itself through this operation.

It is asked for up to eight exact paths. Duplicate, invented or ineligible paths are discarded. Valid AI choices go first; local choices fill the remaining places, to a maximum of ten files total. Selection is not recursive: there is no second search triggered by reading a selected file.

The selector model role is used when compatible with the rewrite route; otherwise the rewrite route’s first model is selected. Copilot rewrites keep selection within Copilot profiles. Non-Copilot rewrites use non-Copilot profiles, which may include different providers. Fallback settings may cause more than one attempted model call, so “one selection stage” is not a guarantee of exactly one billed request.

The picker gets at most 25 seconds, shortened when the run has less time left. If selection fails or returns no valid paths, local choices remain. An empty candidate list skips selection. This extra step can add latency and usage; it does not guarantee better results.

4. Read short snippets from the chosen files

Readable selected files are opened from the project, with a 200,000-byte per-file limit. Recognized credentials are masked before excerpting. The snippet takes the first six keyword hits, with four lines before and two after each, merges overlapping ranges, and adds line numbers. If there are no hits, it starts with up to the first 40 lines.

Each source line is capped at 240 characters; each snippet is roughly 1,400 characters at Relevant code or 1,800 at AI-assisted. Ellipses mark omitted spans. A selected file that is missing, empty, binary, too large or disallowed can be skipped, so the actual count may be lower than six or ten. It is not automatically replaced with another ranked file after a failed read.

What actually reaches the rewriting model

System instructions

The rewriter’s job, English output policy, selected Style, optional Structure, custom instructions and applicable saved rewrite rules. If enabled, target-agent adaptation adds destination-specific guidance.

These are not the Context Level character budget. Saved Rules-tab instructions are different from automatically read project rule files such as AGENTS.md.

User message + attachments

Selected context items are wrapped in <project_context> with kind/label metadata. Your typed task is wrapped in <request>. Explicit file paths are listed; attached text excerpts and supported images are supplied separately from automatic project collection.

Off does not erase explicit inputs or saved rewrite instructions. Attachments have their own limits and are added after automatic context has been budgeted.

What happens when the context is too large?

The automatic items are ordered by priority before fitting the total allowance:

  1. Workspace and Target agent
  2. Instructions, extra files and README
  3. Stack and commands
  4. Selected source snippets
  5. Git status, log and diff
  6. Repository tree

An item that crosses the allowance is shortened if more than 400 characters remain. Otherwise it is skipped; a later, smaller item may still fit. Lower-priority items can disappear. A checked item is eligible, not guaranteed inclusion.

The numbers are approximate characters, not tokens or prices. Truncation markers, wrappers, your request, system instructions and explicit attachments add text outside some of these nominal limits. More context often means more model input, but these budgets cannot predict a charge.

The model is instructed to use context to make the prompt precise, to call search-selected files “likely relevant,” and to avoid inventing paths or commands. The final prompt is not a guaranteed verbatim copy of every included item. Copilot can inspect the actual project later when it acts on the prompt.

The context preview is a checklist, not a frozen payload

  1. Open Options. The list shows item labels, kinds, included character counts and any explanatory notes. Its checkboxes choose exclusions; labels are not expandable content viewers.
  2. Edit the request or change the level. While Options is open and enhancement is idle, changes to the request, target, level, exclusions or context preferences trigger a preview after a short debounce (300 ms).
  3. Refresh context after external file edits. This rereads current project data. It does not rewrite your prompt and makes no model selection call.
  4. Click Enhance. Context is gathered afresh. AI-assisted now runs the file selector when candidates exist, so its final file choices can differ from the preview. Preview also omits the separate attachment processing done for the actual rewrite.

Closing Options hides the controls; it does not clear your choices. A file you uncheck is excluded from automatic rules, tree/listing, source selection and relevant Git diff paths. Unchecking only the tree hides the generated map; it does not disable the inventory needed to find relevant files.

How can I inspect the real files on my computer?

Use the attached session’s project folder as the base. Open that folder in your editor or File Explorer, then open README.md, CONTRIBUTING.md or the listed relative path. These Markdown files are plain text and can be read in Notepad or VS Code.

Workspace, Target agent, Stack and Repository tree are assembled in memory; there is no matching generated file on disk to open. The current panel does not expose the exact assembled context text: the worker sends the preview metadata without its content. Opening an original file shows the source, not the redacted/trimmed version used for enhancement.

Why a source may be missing

Privacy, file safety and exclusions apply at every file-reading level
  • Project-file access disabled: overview/code/AI-assisted requests are reduced to Basic identity-only context. Explicit inputs and saved rewrite rules remain separate.
  • Git disabled: no Git reads, even for listing/search. Filesystem collection and bounded local search remain available.
  • Unknown/remote root: no local project files. The plugin does not guess a different folder.
  • Excluded paths or unchecked files: removed from automatic file candidates and reads; resolved link targets must obey the same policy.
  • Sensitive filenames (such as .env*, private keys and credentials files), binary content and links escaping the project are refused.
  • Missing, unreadable, oversized or unselected files, scan limits and context budgets can leave a source out.

Recognized secrets in automatically included content are masked before shortening. This is pattern-based protection, not a guarantee that every secret or confidential detail can be detected. Typed text and explicit attachments are deliberate inputs with separate handling; turning Context Level off does not remove them.

Copilot host limits: what no context level adds

The installed Copilot canvas integration does not provide terminal scrollback, other agents’ session output, editor-save notifications or recent agent-activity context. Those legacy capabilities contribute nothing here. AI-assisted does not unlock them and does not silently add the full Copilot conversation.

The rewriter sees the assembled request/context, not the destination agent’s complete working environment. Sending the finished prompt is a separate action with attached-session activity, permission and queue checks. Automatic sending remains an explicit opt-in.

Chat auto-enhance follows a separate context switch

This guide’s four levels control the panel’s Enhance workflow. AI chat auto-enhance uses its own Include context in auto-enhance setting. When enabled, it can include Workspace plus permitted instructions, extra files, README and stack information; it omits the tree, source selection, Git changes and the Target agent item described above.

The AI hook also has its own model route: it currently requires an enabled OpenAI-compatible or Anthropic API profile within a short time budget. It does not run the panel’s background Copilot model or Effort assignment. Without an eligible API model it leaves the prompt unchanged. Rules-only auto-enhance simply appends its configured text and does not gather this context.

The Copilot hook prepares fresh static context when enabled; reusable static context is keyed to file preferences and has a 90-second lifetime. The hook does not use the panel’s four total budgets or per-request checkbox list. Saved privacy, extra-file and excluded-path settings still apply. Disabled, ambiguous, failed or timed-out hooks leave the original prompt unchanged and preserve runtime-added context.
