Install GitHub Copilot plugins from your application.

Build a local integration around Copilot’s plugin commands. Let Copilot fetch the package and maintain its installation records; your application selects the source, runs the operation, checks the result, and explains what the user needs to do next.

Target product: the GitHub Copilot desktop app. This guide concerns Copilot’s plugin system. GitHub Desktop is the separate application for working with Git repositories. “Any plugin” here means a package compatible with the target Copilot runtime and its supported components. Copilot app documentation · GitHub Desktop documentation

The installer runs on the user’s computer.

The recommended architecture has four parts. The catalog or repository supplies the plugin; the local CLI performs the installation.

  1. 01Your application

    Shows the source, selected plugin, and target Copilot profile.

  2. 02Local Copilot CLI

    Fetches and registers the package using supported commands.

  3. 03User’s plugin state

    Holds the installed files and their activation settings.

  4. 04Copilot desktop session

    Loads compatible components after discovery or a session reload.

Persistent plugins are discovered by sessions using the same user configuration. An isolated runtime can suppress that discovery. GitHub: persistent and process-scoped plugins

If the application is a desktop app

Use its local process API to invoke Copilot under the signed-in operating-system user. Keep installation operations behind a small, version-aware CLI adapter.

If the application is a website

Provide a local companion/helper or a command handoff. Running Copilot on your web server would install into the server’s profile. One browser integration option is an extension connected to an installed native messaging host; a normal webpage does not get that capability by itself.

Keep the repository, marketplace, and plugin identities separate.

A marketplace is a catalog. Its repository can contain several plugins or point to other sources. The marketplace’s declared name is the registration key; it need not match the repository name. Read the catalog and CLI output rather than deriving names from the URL. GitHub: marketplace structure

Marketplace sourceacme/copilot-catalogGitHub repository containing the catalog. Shorthand avoids a full URL.
Marketplace nameteam-toolsThe catalog’s declared identity.
Plugin namereview-helperThe plugin selected from that catalog.
Qualified plugin identityreview-helper@team-toolsThe marketplace installation target.

All examples are placeholders. Substitute a real source and the identities it declares.

For your application’s records, keep the source type, original source, declared names, installation mode, selected Copilot profile, and last verified state as distinct fields. Track the runtime version used for each operation. Treat plugin metadata as display data, never as executable instructions for your installer.

Use a marketplace when you want a catalog; install directly when you already have a plugin.

The marketplace route supports browsing and selecting among entries. A direct repository installation does not need a separate marketplace registration. GitHub supports both approaches. GitHub: finding and installing plugins

Marketplace route

Commands use copilot for readability. The application should invoke its resolved executable path. In PowerShell, a quoted executable path is invoked with &.

copilot plugin marketplace list --json

# Register only if this source is not already registered.
copilot plugin marketplace add acme/copilot-catalog

# Read the declared name; do not assume it is "copilot-catalog".
copilot plugin marketplace list --json
copilot plugin marketplace browse team-tools --json

copilot plugin install review-helper@team-tools
copilot plugin list --json

Execute one operation at a time and check its exit status before continuing. After registration, confirm that the declared marketplace name resolves to the intended source. If an existing name points elsewhere, report the conflict instead of replacing it.

The list and browse JSON options are documented in the CLI plugin reference; confirm them against the selected executable’s help.

Direct plugin route

# Plugin at the repository root:
copilot plugin install acme/review-helper

# Plugin inside a larger repository:
copilot plugin install acme/tool-collection:plugins/review-helper

# A Git URL is also an accepted source:
copilot plugin install https://github.com/acme/review-helper.git

OWNER/REPO is sufficient for GitHub; a full Git URL is useful for other hosts. The target must contain an installable plugin. Pointing the direct route at a catalog-only repository does not select one of its entries. Accepted source formats

Local folders: distinguish a cached install from live development

Where supported by the selected runtime, copilot plugin install ./my-plugin installs a cached copy; reinstall to pick up source changes. Local plugin testing

A path-sourced plugin in a local directory marketplace loads from its actual source directory. Keep that directory in place and reload the session after rebuilding. Live local marketplace behavior

Expose this as an intentional development mode. For ordinary users, prefer a published package with all required runtime files already included. Do not run a repository’s build scripts merely because files are missing.

Update, disable, enable, and remove

copilot plugin update review-helper@team-tools
copilot plugin disable review-helper@team-tools
copilot plugin enable review-helper@team-tools
copilot plugin uninstall review-helper@team-tools

Use the identity appropriate to the installation mode. Re-read the installed inventory after every mutation. Keep “Update” separate from “Install,” and preserve an existing disabled state unless the user requests activation. These lifecycle operations are described in GitHub’s management guide.

Find a supported executable and target the same profile as the desktop app.

The executable and configuration directory are part of the integration contract. A command can succeed against the wrong profile and leave the user’s desktop unchanged.

  1. Resolve an executable. Support a user-configured absolute path, then discovery through PATH. Validate the executable’s identity, version, and plugin capabilities before accepting it. Revalidate when the selected executable changes.
  2. Offer CLI setup if it is missing. GitHub publishes Windows, macOS, and Linux installation methods. On Windows, its documented WinGet command is winget install GitHub.Copilot. Do not assume installing the desktop app put copilot on PATH. Official CLI setup
  3. Avoid depending on a bundled runtime’s versioned folder. A desktop-bundled executable may be usable, but its internal location is not a durable discovery contract established by the cited docs. Keep any such fallback in an explicitly tested adapter; never choose an arbitrary cached version.
  4. Use the desktop user’s configuration. The default is ~/.copilot; COPILOT_HOME overrides it. A different account, elevated service, or custom home can target another installation. Show the selected profile in the app. Configuration directory rules
  5. Check compatibility with the desktop release. A CLI can accept a package whose desktop components need a different host version. Test the CLI/desktop combinations you support; successful installation alone does not establish component compatibility.
# Read-only capability probes for the selected executable:
copilot --version
copilot plugin --help
copilot plugin install --help
copilot plugin marketplace --help
copilot plugin list --json

Use a controlled working directory for global inventory operations. Repository-specific activation should be checked in the actual target repository and presented separately. Do not inherit an unrelated repository context from your application’s installation folder.

A process-only plugin mount is a different operation. --plugin-dir applies to the runtime process launched with that argument. Passing it to your own SDK client does not persistently install the plugin for a separately running desktop app. GitHub: plugin loading scope

Use filesystem locations for diagnosis, and CLI commands for installation.

On Windows, the default Copilot home is %USERPROFILE%\.copilot. On macOS and Linux it is ~/.copilot. A configured COPILOT_HOME replaces that root. The cache is separate and can be overridden by COPILOT_CACHE_HOME. GitHub: configuration and cache directories

<Copilot home>/
├── installed-plugins/
│   ├── <marketplace>/<plugin>/     marketplace install
│   └── _direct/<source-id>/        direct install
├── config.json                    Copilot-managed internal state
├── settings.json                  user settings
└── plugin-data/                    persistent plugin data

Installed package layout: CLI file locations. State and settings roles: configuration directory reference.

The managed state includes installation records; user settings include activation and marketplace configuration. Your installer should let the CLI maintain them. Copying a package into the cache does not complete this managed workflow. Avoid treating today’s JSON structure or cache naming as a stable API.

What belongs inside a package?

Agent Plugins packages use a root plugin.json. Components can include skills/, mcp.json, and client-specific files under com.github.copilot/. Legacy plugins use other supported conventions. GitHub: plugin authoring

A canvas package must include the executable extension and the resources its interface needs. A skill-only package will have a different layout. Preserve the published package as a unit; do not manufacture a canvas directory or strip “unused” files from every plugin.

Plugin authors may use additional storage locations or external services. Treat the package, cached catalog, and user data as separate things. Uninstalling is not a promise to erase every credential or data file a plugin has ever created.

Make installation a verified state change.

The following is a proposed application design, not a GitHub SDK API. It keeps source selection, process execution, and result interpretation separate so each can adapt to runtime changes.

installPlugin(selection, targetProfile):
    runtime = resolveAndProbeRuntime(targetProfile)
    before = readPluginInventory(runtime, targetProfile)

    if selection uses a marketplace:
        ensure source is registered without a name/source conflict
        resolve catalog identity and chosen plugin

    if the same installation already exists:
        report its current state; offer update or enable when appropriate
        return

    run install with validated arguments
    require successful process completion
    after = readPluginInventory(runtime, targetProfile)
    verify the intended identity and available source metadata

    report installed + activation state
    explain reload and any remaining setup

Process adapter requirements

ConcernImplementation recommendation
ArgumentsUse the process API’s executable and argument array. Validate source types and reject option-like source strings. Avoid assembling shell commands from catalog metadata.
Windows launchersHandle native executables and package-manager wrappers deliberately. A .cmd shim has different launch requirements; do not silently enable a shell for arbitrary input.
CompletionCollect the exit status and bounded output. Handle launch errors, cancellation, timeout, and process exit. A progress message is not a completion signal.
ConcurrencySerialize mutations for each target profile within your app. Re-read state after completion or interruption; another app or the user may have changed it.
AuthenticationUse Copilot’s supported sign-in flow and the user’s repository access. Return an “Action required” state if interaction is needed; resume verification after the user completes it.
Prompts and trustShow the source and requested install action before starting. Preserve runtime confirmations. A generic, fully unattended install of every source type is not an assumption this design makes.
LogsKeep operation, runtime version, exit status, and a sanitized error excerpt. Avoid storing credentials, token-bearing URLs, or full configuration files.
ParsingUse version-tested JSON readers. Current plugin lists use an array; older output used an object with a plugins field. Validate fields and surface errors. Unknown output must not be interpreted as an empty inventory.

Process API details: Node.js child processes (one implementation option). JSON evolution: Copilot CLI reference. Authentication: GitHub CLI sign-in guidance.

If the front end uses a local helper, give that helper a narrow operation API such as “list” and “install validated source.” Authenticate the local channel and authorize each requesting origin. It should not expose a general-purpose “run this shell command” endpoint.

Tell the user which state was actually verified.

App statusEvidence and next step
InstalledThe command succeeded and the expected plugin appears in inventory. Show its reported version and activation state.
Installed, disabledThe plugin exists but is off. Offer enablement if permitted and requested; preserve intentional disablement.
Reload neededInventory is correct but the existing desktop session may not have rediscovered it. Ask the user to start a new session or restart the app; do not terminate active work automatically.
Setup requiredInstallation completed, but a component needs credentials, a runtime dependency, or other documented setup.
Blocked or incompatibleExplain the reported policy, schema, component, or host-version constraint. Provide a relevant fix or supported-version requirement.
Failed or interruptedShow a useful cause. Reconcile inventory before offering retry; registration may already have succeeded even when a later step failed.

Repository settings can change effective activation, and managed settings can require or block plugins. Do not attempt to defeat those settings by editing internal state. GitHub: desktop plugin activation and policy

For retry and recovery, keep a small operation journal in your own application: target profile, requested identity, sanitized source, steps completed, and last verification result. Do not delete a marketplace automatically after a failed install; other plugins may use it. Never use a forced marketplace removal as cleanup.

Ship against tested runtime and desktop combinations.

Use a disposable Copilot profile and a small, harmless test plugin for installer tests. Verify desktop loading separately with a test account/profile. The following is a proposed release test matrix for the integrating application.

  • Fresh install, repeat install, update, disable, enable, and uninstall.
  • Repository name differs from marketplace name; multiple plugins share one catalog.
  • Same marketplace name points to a different source.
  • CLI missing, outdated, moved, or updated while the app is open.
  • Executable and profile paths contain spaces and non-ASCII characters.
  • Private repository access, signed-out user, and interrupted authentication.
  • Network loss, cancellation, and application crash between registration and install.
  • JSON output variations and malformed or unknown output.
  • Default profile versus custom home; global versus repository activation.
  • Managed block, unsupported plugin format, and unsupported desktop component.
  • A harmless skill, a canvas where supported, and a component with external setup.
  • New-session discovery in each supported desktop/CLI version pair.

Keep CLI-specific parsing and executable discovery in one adapter. Test that adapter before adding support for a new runtime release, and retain diagnostics that identify the desktop and CLI versions involved. Where no documented desktop inventory API is available to your app, keep desktop readiness as a separate manual acceptance check.

Recommended product promise: “Install compatible plugins into your selected GitHub Copilot profile and verify their installation status.” Claim a plugin is ready to use only after its component setup and desktop loading have been verified.
